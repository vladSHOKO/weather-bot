# Эксплуатация

## Контейнерное развёртывание

Использовать отдельный каталог и явно выбранное имя Compose-проекта. Перед подключением существующего тома проверить имя проекта и резервную копию; новое имя проекта создаёт другой том.

1. Подготовить защищённый `.env`. В `DATABASE_URL` использовать `weather_app`, в `GOOSE_DBSTRING` — `weather_migrator`, для обеих строк хост `db`. Не переносить локальные URI с хостом `127.0.0.1` в контейнеры.
2. Запустить только БД, создать роли и задать пароли:

```bash
docker compose -f compose.deploy.yml up -d db
make db-roles COMPOSE='docker compose -f compose.deploy.yml'
make db-passwords COMPOSE='docker compose -f compose.deploy.yml'
```

3. Для существующей БД передать владельцев по [инструкции БД](database-security.md). Сделать backup до изменения схемы.
4. Собрать и запустить отдельную задачу миграций, выдать права, затем запустить приложение:

```bash
docker compose -f compose.deploy.yml --profile tools build migrate
docker compose -f compose.deploy.yml --profile tools run --rm migrate
make db-grants COMPOSE='docker compose -f compose.deploy.yml'
docker compose -f compose.deploy.yml up -d --build bot
```

Пароли в этих командах не передаются аргументами; Compose читает `.env`. Не публиковать вывод `docker compose config` и `docker inspect`, поскольку он может содержать секреты. Вместо вывода содержимого конфигурации проверять её через `docker compose ... config --quiet`.

Миграции не запускаются каждым экземпляром бота. Приложение проверяет маркер нужной схемы через read-only view `bot_schema_version`, не получая доступа к таблице goose. БД привязывается к ID бота из `getMe`; ротация токена того же бота допустима, другой бот должен использовать другую БД.

БД не публикует порт, находится в сети `internal`. Приложение имеет отдельную сеть для внешних HTTPS API. Для удалённой БД дополнительно настроить firewall и TLS с проверкой CA/имени. Контейнер работает от UID 65532, с read-only filesystem, без capabilities; `/tmp` — временный tmpfs.

Остановка:

```bash
docker compose -f compose.deploy.yml stop
```

SIGTERM отменяет poller, текущие запросы и ожидания; незавершённые события останутся в PostgreSQL. `stop_grace_period` нужно держать больше выбранного периода завершения. По умолчанию сервер health закрывается в пределах 15 секунд. Пределы HTTP/БД обеспечивают ограниченность внешних ожиданий.

Не откатывать схему автоматически при остановке или откате бинарника. Down новой миграции удаляет inbox/checkpoint и потому пригоден только для тестового окружения либо отдельной согласованной процедуры. Для обновления приложения: backup → миграция → выдача прав → новая версия → проверка health и команд. Старый бинарник может быть несовместим с новой схемой; совместимость проверить до отката.

## Наблюдение и минимальные сигналы

Проверка readiness внутри контейнера:

```bash
docker compose -f compose.deploy.yml exec -T bot weather-sum -healthcheck
```

На хостовом запуске доступны `http://127.0.0.1:8080/healthz` и `/metrics`. Не открывать эти endpoint наружу; для внешней системы мониторинга использовать защищённый агент/туннель. JSON содержит суммарные счётчики команд, ошибок, времени выполнения, запросов источников, попаданий кеша и ограничений частоты, а также размеры состояний очереди. Счётчики процесса сбрасываются при рестарте.

Правила для системы мониторинга оператора:

- Три неуспешные readiness-проверки с интервалом 10 секунд — проверить БД и процесс.
- Рост ожидающих событий в течение 5 минут либо очередь выше 80% ёмкости — проверить API, квоты, время ответов и число исполнителей.
- Рост failed или доля ошибок попыток выше 10% за 5 минут — проверить безопасные классы ошибок и доступность источников.
- Отсутствие успешной резервной копии за 26 часов — проверить задание backup.

Оповещения в сторонние сервисы не отправляются самим ботом. Подключение системы мониторинга и адресатов выполняется оператором при развёртывании.

Начальные лимиты — 4 исполнителя, 1000 событий, 20 незавершённых событий на чат и 5 внешних запросов/с. Повышать их после измерений на целевом сервере и проверки квот API. Разные чаты независимы, порядок команд одного чата сохраняется. При потере соединения, удерживающего poller lock, процесс завершает работу после heartbeat; использовать один Compose-экземпляр, не запускать несколько обработчиков этой БД вручную.

## Резервное копирование и удаление данных

Скрипт `scripts/backup.sh` делает логический dump БД через контейнер. Файлы содержат пользовательские данные: хранить каталог с ограниченным доступом, на рабочем сервере — на шифрованном диске или в зашифрованном хранилище. Скрипт не реализует шифрование и не копирует данные во внешние сервисы.

Dump сначала пишется во временный файл. После успешного `pg_dump` скрипт проверяет непустой архив через `pg_restore --list` и атомарно публикует его без перезаписи существующего имени. Только затем удаляются старые копии. При ошибке временный файл удаляется; после SIGKILL может остаться скрытый `.partial`, который не считается готовой копией. Проверка списка архива не заменяет пробное восстановление.

```bash
COMPOSE_FILE=compose.deploy.yml bash scripts/backup.sh
```

Политика по умолчанию — ежедневная копия, хранение 14 дней. Скрипт удаляет только файлы собственного шаблона `weather-sum-*.dump` старше 14 дней в выбранном каталоге после успешного создания новой копии. Задание нужно добавить в планировщик сервера; локально планировщик не устанавливается. Перед изменением срока согласовать требования к восстановлению и уведомить пользователей о сроке удаления данных из копий. Не считать ротацию выполненной, пока задание фактически не работает.

Не реже раза в месяц восстанавливать копию в отдельной БД через `pg_restore`, проверять `user_locations`, `bot_state` и незавершённые `bot_updates`. В интеграционном стенде восстановление уже автоматизировано. На рабочей БД для проверки восстановления не выполнять `DROP DATABASE` и не удалять том.

Восстановленная копия может содержать ранее удалённые локации и старые события. До подключения восстановленной БД к реальному боту нужно применить журнал удалений/действующую политику восстановления и решить, какие pending-события ещё актуальны. После восстановления старого checkpoint часть внешних отправок может повториться. Без отдельного журнала удалений вне backup нельзя обещать сохранение удаления при восстановлении старой копии.

## Проверки после настройки

Проверить фактические права роли приложения, логин по новым паролям, отсутствие публикации БД и отсутствие секретов в реальных логах. На отдельном тестовом Telegram-боте пройти `/start`, поиск и подтверждение города, `/weather`, частичный отказ источника, удаление локации и перезапуск. Требуются реальные ключи и внешняя сеть; автоматические тесты используют поддельные ответы API.

Проверку истории Git выполнять на полном репозитории, например `gitleaks git --redact --log-opts='--all'`. Если секрет раскрывался, заменить его и ограничить доступ к старым логам/копиям. Не ограничиваться добавлением файла в `.gitignore`.

Условия использования, коммерческие тарифы, атрибуцию поставщиков и доступные квоты проверить для выбранных аккаунтов перед выпуском. Работоспособность публичного endpoint не подтверждает разрешение коммерческого использования.
