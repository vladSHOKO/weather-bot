# БД и секреты

Обычный `make stop` останавливает контейнеры и сохраняет данные. Откат миграций и удаление томов в остановку больше не входят.

## Секреты и запуск локальной БД

Если `.env` уже существует, редактировать его, не копировать поверх него шаблон. Для нового окружения:

```bash
cp .env.example .env
chmod 600 .env
```

Заполнить `POSTGRES_PASSWORD` случайным уникальным паролем. Сгенерировать значение можно локально через `openssl rand -hex 32`. Не публиковать вывод и содержимое `.env`. Параметры БД по умолчанию: `POSTGRES_USER=postgres`, `POSTGRES_DB=application`, `POSTGRES_PORT=5432`.

```bash
make start
make db-roles
make db-passwords
```

`make db-roles` предназначен для отдельной БД этого проекта. Он создаёт `weather_migrator` и `weather_app`, ограничивает создание объектов через `PUBLIC` и выдаёт роли миграций доступ к схеме. Роли с административными атрибутами или членством в других ролях не переиспользуются: скрипт прерывается. Проверить также отсутствие прежних прямых прав и владения объектами, если эти имена уже использовались раньше. Скрипт не является очисткой произвольной существующей модели доступа.

`make db-passwords` интерактивно запросит новые пароли для обеих ролей через `psql \password`. Ввод скрыт, пароль не передаётся аргументом процесса и не хранится в SQL-файле. Команда требует терминал. Для автоматизации использовать отдельное защищённое управление секретами.

В `.env` заполнить строки подключения, используя заданные пароли:

```dotenv
# Значения в угловых скобках заменить; это не готовые реквизиты.
DATABASE_URL=postgres://weather_app:<app-password>@127.0.0.1:5432/application?sslmode=disable
GOOSE_DBSTRING=postgres://weather_migrator:<migration-password>@127.0.0.1:5432/application?sslmode=disable
```

Специальные символы паролей в URI нужно percent-encode. `sslmode=disable` допустим здесь только для локального подключения. Не выводить строки подключения при диагностике.

Установить goose и убедиться, что он доступен в PATH, либо передать путь: `make migrate GOOSE=/home/vladislav/go/bin/goose`. Goose читает `GOOSE_DBSTRING` из `.env`; Makefile не вставляет пароль в аргументы команды.

```bash
make migrate
make db-grants
```

Миграции принадлежат `weather_migrator`, бот использует `weather_app`. Выдаются `SELECT`, `INSERT`, `UPDATE`, `DELETE` для `user_locations`, `bot_state` и `bot_updates`, а также `SELECT` на view `bot_schema_version`. Доступ к таблице истории goose не предоставляется. `db-grants` выполняется после миграций; ошибка отсутствующей таблицы не скрывается.

Для проверки прав приложения подключиться как `weather_app`: чтение/запись локации должны работать, `DROP TABLE`, создание таблиц/схем/ролей и доступ к `goose_db_version` — завершаться отказом. Не проверять удаление объектов на рабочей БД.

## Существующая БД: без сброса тома

Изменение `POSTGRES_PASSWORD` в Compose не меняет пароль уже существующего пользователя PostgreSQL. Файлы и том не удалять.

1. Сделать резервную копию защищённым инструментом и проверить её восстановление на отдельной БД.
2. Сохранить прежнее имя Compose-проекта и тома. Новое имя проекта может создать пустой том вместо подключения существующего.
3. Заполнить параметры Compose и запустить контейнер с прежним томом. Доступ через локальный сокет из контейнера стандартного образа PostgreSQL используется для администрирования; при изменённом `pg_hba.conf` потребуется соответствующий способ аутентификации.
4. Выполнить `make db-roles`, затем `make db-passwords`.
5. Проверить владельца `user_locations` и таблицы версии goose. Если они принадлежат прежнему администратору, передать их `weather_migrator` из административного сеанса. При нестандартном имени таблицы goose использовать её реальное имя:

```sql
BEGIN;
ALTER TABLE public.user_locations OWNER TO weather_migrator;
ALTER TABLE public.goose_db_version OWNER TO weather_migrator;
ALTER TABLE IF EXISTS public.bot_state OWNER TO weather_migrator;
ALTER TABLE IF EXISTS public.bot_updates OWNER TO weather_migrator;
ALTER VIEW IF EXISTS public.bot_schema_version OWNER TO weather_migrator;
COMMIT;
```

6. Выполнить `make db-grants`. Проверить возможность запуска миграций и операции бота с новыми ролями, затем заменить `DATABASE_URL`/`GOOSE_DBSTRING` в `.env` и перезапустить бот.
7. Для смены прежнего слабого пароля администратора открыть защищённый сеанс psql и выполнить `\password postgres` (либо фактическое имя администратора). Согласованно обновить хранимые реквизиты. Одна замена строки в `.env` недостаточна.
8. Проверить сохранность записей, отсутствие подключений бота от администратора и недоступность порта БД с другого хоста.

Если старая роль приложения владеет и другими объектами, или БД обслуживает другие приложения, перед изменением прав составить отдельный список владельцев и зависимостей. Не выполнять массовый отзыв прав на общем сервере без этой проверки.

## Сеть и удалённая БД

`compose.yml` публикует PostgreSQL только на `127.0.0.1` и предназначен для локальной разработки. В подготовленном `compose.deploy.yml` БД находится во внутренней сети без секции `ports`; имя хоста в строке подключения меняется на `db`. Выбор и приёмка рабочего окружения выполняются отдельно перед выпуском.

Для удалённого PostgreSQL использовать проверяемый TLS, например `sslmode=verify-full` с доверенным CA и подходящим именем сервера. Проверить firewall отдельно. Локальный успешный тест не подтверждает сетевую изоляцию рабочего сервера.

## Полный сброс только локальных данных

Для удаления всего локального тома предусмотрена отдельная команда:

```bash
make reset-local APP_ENV=development CONFIRM_RESET=DELETE_LOCAL_DATA
```

Она необратимо удаляет данные выбранного Compose-проекта. Перед выполнением проверить Docker context, `.env`, имя проекта и наличие необходимых копий. Без обоих значений команда отказывается работать; эти проверки не определяют автоматически, куда направлен Docker context.

## Проверки и ограничения

```bash
go test ./...
go vet ./...
bash tests/integration/block-01.sh
```

Интеграционная проверка создаёт отдельный Compose-проект со случайным паролем и временным локальным портом. После проверки удаляются только её контейнеры и том. Рабочий `.env` не загружается. Проверяются CRUD от имени роли приложения, запрет DDL и доступа к метаданным миграций, сохранность записи после `make stop`/`make start`, привязка loopback и защита сброса. Проверка привилегий использует `SET ROLE`; интерактивная установка паролей и вход по ним проверяются отдельно при настройке реального окружения.

Ошибки приложения с секретами представлены безопасной операцией и категорией, без исходного URL, произвольного текста сервера и строки подключения. Причина сохраняется через `Unwrap` для `errors.Is`/`errors.As`; извлекать и логировать её напрямую нельзя. Структурированные логи и ограниченный набор `failure_code` уже реализованы; значения описаны в README.

Пользователь подтвердил, что Git-история проекта пока не ведётся. Исходники проверены Gitleaks; при создании или импорте репозитория выполнить `make check-secrets`, включая историю. Если в истории/логах найдены секреты, заменить затронутые ключи; добавление `.gitignore` не удаляет секреты из прошлых коммитов. Установленные локально права `.env` не переносятся автоматически при копировании или создании нового файла.
