# Аудит weather-sum

Дата: 18 октября 2026 года. Объект: доступная локальная копия проекта.

## 1. Вывод

Проект имеет подходящую для небольшого Telegram-бота структуру: получение погоды, геокодинг, хранение и отображение разделены; внешние сервисы подключаются через интерфейсы. Однако текущую версию нельзя считать готовой к публичной эксплуатации: есть ошибки расчёта прогноза, блокировка очереди сообщений при сбоях, риск попадания токена в логи и опасная команда остановки, удаляющая данные.

Главный приоритет — достоверность ответа и устойчивость обработки сообщений. Расширять набор погодных функций стоит после исправления этих проблем и появления регрессионных тестов.

Подтверждённой возможности удалённого исполнения кода или SQL-инъекции не обнаружено. Это заключение ограничено исследованным кодом и не означает отсутствия любых уязвимостей. Доступность БД извне, фактические права production-пользователя, состояние секретов и наличие известных уязвимостей зависимостей полностью не проверены.

## 3. Безопасность

### S1. Слабый пароль БД и публикация порта на интерфейсах хоста

**Риск: высокий при сетевой доступности хоста. Приоритет: P1. Статус: конфигурация подтверждена, доступность извне не проверялась.**

Места: `compose.yml:7–11`, `Makefile:4`.

Compose задаёт пользователя `postgres`, пароль `password` и публикацию `5432:5432` без ограничения адресом loopback. Если этот вариант запуска используется на доступном сервере, а firewall пропускает соединения, БД можно атаковать с известными реквизитами. Учётная запись, созданная через `POSTGRES_USER` стандартного образа, обладает широкими правами; использовать её для бота избыточно.

Рекомендации: для разработки публиковать `127.0.0.1:5432:5432`; для контейнеризированного приложения по возможности оставить БД только во внутренней сети. Убрать фиксированный пароль, завести отдельную роль приложения с необходимыми операциями над `user_locations`, а миграции выполнять отдельной ролью. Для удалённой БД настроить проверяемый TLS; `sslmode=disable` из Makefile оставить только явно локальным сценарием.

**Проверка исправления:** порт недоступен с другого хоста; роль бота не может создавать/удалять таблицы; в файлах запуска нет фиксированного рабочего пароля. Смена переменных Compose сама по себе не меняет пароль уже инициализированного PostgreSQL-тома — потребуется отдельная смена реквизитов в БД.

### S2. Токен Telegram может попадать в логи через HTTP-ошибки

**Риск: высокий при доступе посторонних к логам. Приоритет: P1. Статус: воспроизведено с вымышленным токеном.**

Места: `internal/bot/bot.go:47–62,90–97`, `internal/bot/handlers.go:52–59`. Аналогичная потенциальная утечка ключа OpenWeather: `internal/weather/open_weather.go`, метод `Forecast`.

Токен включается в путь URL Telegram, ключ OpenWeather — в query string. Ошибка `http.Client.Do` может содержать URL. Эти ошибки без очистки доходят до `fmt.Println(err)` в обработчике. При имитации сетевой ошибки `GetUpdates` вернул строку с вымышленным токеном. Реальная компрометация секретов не установлена.

Рекомендация: перед выводом очищать URL в цепочках ошибок, скрывать и путь `bot<TOKEN>`, и параметр `appid`; записывать безопасные поля: сервис, операция, класс ошибки, HTTP-статус. Не полагаться только на запрет логирования заголовков: здесь секреты находятся в URL.

**Проверка исправления:** ошибки DNS, соединения, TLS и тайм-аута обоих API не содержат тестовых секретов в логах. Если утечка подтвердится в реальных логах — заменить соответствующие ключи и ограничить доступ к сохранённым логам.

### S3. Локальный файл секретов недостаточно защищён от случайного распространения

**Риск: средний, зависит от локальных пользователей и способа публикации. Приоритет: P2. Статус: подтверждено наличие `.env` с правами `0644` и отсутствие `.gitignore`.**

На обычной файловой системе права `0644` разрешают чтение другим локальным пользователям при доступности родительских каталогов. Отсутствие `.gitignore` повышает риск случайного добавления `.env`, бинарников и локальных данных. Наличие файла само по себе не доказывает утечку; историю Git проверить невозможно.

Рекомендации: выставить ограниченные права для `.env`, добавить правила игнорирования секретов и артефактов, проверить историю настоящего репозитория сканером секретов. Если секрет уже отслеживается Git, одного `.gitignore` недостаточно. Для контейнерной сборки добавить `.dockerignore` и исключить секреты из образа.

### S4. Один пользователь может занимать общую очередь и расходовать квоты API

**Риск: средний; усиливается проблемой F1. Приоритет: P2. Статус: подтверждено по коду, нагрузочные испытания не проводились.**

Места: `internal/bot/handlers.go:68–99,111–154`, `internal/weather/service.go:80–137`.

Обработка сообщений последовательная. Каждый `/weather` запускает оба погодных запроса, каждый `/setlocation` — геокодинг и запись. Нет ограничений частоты по чату, общего бюджета запросов, кеша или объединения одинаковых запросов. Медленные запросы одного пользователя задерживают остальных; частые команды расходуют квоты поставщиков.

Рекомендации: лимиты по чату и на приложение, ограниченная очередь задач, кеш прогноза по координатам и периоду с небольшим TTL, объединение одновременных одинаковых запросов. При добавлении конкурентности сохранять порядок команд внутри одного чата и ограничивать число исполнителей.

### S5. Нет явной политики групповых чатов и удаления сохранённой локации

**Риск: низкий/средний в зависимости от требований продукта. Приоритет: P2. Статус: свойство реализации; нарушение доступа зависит от выбранной политики.**

Места: `internal/bot/bot.go:79–86,120–123`, `internal/storage/postgres.go:19–35`, SQL-миграция.

Хранение привязано к `chat_id`. В группе это общая локация: любой участник, чья команда доставлена боту, может её изменить. Модель входящего сообщения не сохраняет тип чата и автора, поэтому проверять полномочия сейчас нечем. Для личных чатов такое хранение естественно; называть это безусловным обходом авторизации неправильно.

Рекомендации: явно выбрать поддержку только личных чатов либо правила изменения групповой локации. Добавить удаление своих данных, объяснение хранения и резервного копирования. Ключи чужих чатов клиент напрямую не передаёт — они берутся из ответа Telegram.

### S6. Защитные ограничения внешних ответов не заданы

**Риск: низкий при доверенных провайдерах. Приоритет: P2. Статус: подтверждено по коду.**

JSON читается из `resp.Body` без ограничения размера. Для координат, вероятностей, пустой timezone и обязательных полей нет полноценной валидации. Это прежде всего устойчивость к некорректному ответу внешнего сервиса, а не обнаруженный прямой путь атаки обычного пользователя.

Рекомендации: ограничивать размер ответов по ожидаемому API, проверять схему и значения, различать отсутствующее значение и ноль. Для nullable-полей использовать указатели или аналогичный тип, а не неявное превращение `null` в нулевые значения.

### Уже реализованные защитные свойства

- SQL использует параметры `$1…$5`; конкатенации пользовательского ввода в SQL нет.
- Название города кодируется через `url.QueryEscape`; адрес геокодера фиксирован.
- Погодные запросы используют фиксированные HTTPS-хосты и числовые координаты. Прямого пользовательского управления адресом запроса не найдено.
- `parse_mode` для Telegram не задан, поэтому интерпретации пользовательского текста как HTML/Markdown в текущем выводе нет.
- HTTP-запросам передаётся контекст, тела ответов закрываются; стандартный тайм-аут клиента — 5 секунд.
- При разборе Open-Meteo проверяется совпадение длин массивов, что предотвращает соответствующий выход за границы.

## 4. Функциональность и надёжность

### F1. Ошибка одного сообщения блокирует обработку последующих

**Влияние: высокое. Приоритет: P1. Статус: прекращение обработки пачки воспроизведено; повторная обработка следует из управления offset.**

Место: `internal/bot/handlers.go:50–63,68–99`.

`SolveHandler` возвращается при первой ошибке. `Run` после этого делает `continue`, не обновляя `offset`. Следующий запрос получает ещё не подтверждённую пачку. Успешные действия в начале пачки могут повторяться, а сообщения за проблемным не обрабатываются. Сценарии: постоянная ошибка `/weather`, отказ БД или отказ отправки сообщения. Изолированная проверка с двумя `/start` подтвердила: отказ отправки первому чату не позволяет дойти до второго.

Рекомендация: сохранять `update_id` у каждого события, обрабатывать ошибки отдельно, ограничивать повторы и выводить проблемное событие из основного потока после исчерпания попыток. Подтверждать только обработанные либо надёжно сохранённые события. Для долговечной очереди хранить событие и checkpoint согласованно. Не просто продвигать offset заранее: это создаст потерю необработанных сообщений при падении.

**Критерий:** постоянная ошибка одного чата не мешает ответу другому; успешные сообщения не переисполняются бесконечно.

### F2. Частичная недоступность поставщиков срывает весь прогноз

**Влияние: высокое. Приоритет: P1. Статус: воспроизведено.**

Места: `internal/weather/service.go:71–163`, `main.go:51`, `internal/weather/open_weather.go`, проверка API-ключа.

Первая ошибка вызывает `cancel()` для остальных запросов, а затем возвращается из `GetTodayWeather`. Даже успешные данные второго источника не используются. Пустой ключ OpenWeather приводит к этому на каждом `/weather`, поскольку провайдер всегда добавляется в `main`. Это расходится с заявленной в плане graceful degradation и усиливает F1.

Рекомендация: сохранять имя, индекс, состояние и безопасную причину ошибки каждого источника; не отменять независимые запросы из-за одного сбоя. Формировать прогноз по доступным данным, явно указывая ограниченность; возвращать ошибку при отсутствии пригодных данных. Опционального поставщика не подключать без ключа либо требовать ключ при старте, если оба обязательны.

**Критерий:** при одном ответе и одном отказе пользователь получает прогноз с отметкой «1 из 2 источников»; отказ всех источников не выдаётся за сухую погоду.

### F3. Open-Meteo и OpenWeather агрегируются за разные периоды

**Влияние: высокое для смысла прогноза. Приоритет: P1. Статус: воспроизведено на поддельном ответе API.**

Места: `internal/weather/open_meteo.go:32–57`, `internal/weather/service.go:51–68,86–124`, фильтрация в `internal/weather/open_weather.go`.

Сервис задаёт период от текущего времени до следующей полуночи. OpenWeather фильтрует точки по этому периоду, Open-Meteo возвращает весь день, а сервис дополнительно не фильтрует. Утренний дождь может влиять на вечерний совет взять зонт. Проверка запроса на 17:00–24:00 вернула также точку 01:00.

Рекомендация: определить продуктовый смысл «сегодня» — весь день или остаток дня — и применять единый контракт периода на уровне сервиса. Для интервальных осадков проверять пересечение интервалов, а не только момент точки. Отображать реальный горизонт, например «с 17:00 до 24:00».

### F4. Неправильно вычисляются минимальная и максимальная температуры

**Влияние: среднее. Приоритет: P1. Статус: оба сценария воспроизведены.**

Место: `internal/weather/service.go:92–109,166–185`.

Ноль используется как признак неинициализированного экстремума. Для точек `[0, 5]` минимальная температура источника становится `5`. При сводке максимум начинается с `0`, поэтому максимум единственного источника `−5` превращается в `0`.

Рекомендация: инициализировать экстремумы первой валидной точкой/источником либо использовать явный признак наличия значения. Недоступные и пустые источники исключать до расчётов.

**Критерий:** случаи `[0, 5]`, `[−5, 0, −2]`, полностью отрицательные значения и единственная точка возвращают реальные экстремумы.

### F5. Пустой прогноз ошибочно означает доступный источник и отсутствие дождя

**Влияние: среднее. Приоритет: P1. Статус: воспроизведено.**

Место: `internal/weather/service.go:86–135,268–298`.

Провайдер может успешно вернуть пустой срез, например OpenWeather после поздневечерней фильтрации. Источник всё равно получает `IsAvailable=true`, температуры остаются нулевыми, а рекомендация может стать «зонт не нужен». Сервис без провайдеров также возвращает успешный результат с нулевыми температурами, хотя совет в этом случае уже сообщает о нехватке данных.

Рекомендация: отличать «нет данных», «неизвестно» и «дождя не ожидается». Учитывать покрытие периода и количество валидных точек, не вычислять сводку по пустым данным.

### F6. Признак дождя и совет по зонту противоречат друг другу

**Влияние: среднее. Приоритет: P1. Статус: два сценария воспроизведены.**

Место: `internal/weather/service.go:111–121,188–205,228–240,268–298`.

Используются разные правила:

- `RainDetected`: любая вероятность больше нуля или любое положительное количество дождя.
- Ненулевой риск интервала: вероятность от 20% либо положительное количество дождя.
- `HasRain`: дождь обнаружен всеми источниками и существует хотя бы один рискованный интервал.
- Совет по зонту: зависит от максимального риска либо доли «дождливых» источников.

Следствия: при вероятности 1% у обоих источников получается «дождь: false», интервалов нет, но «зонт: yes» с причиной высокой вероятности. При вероятности 80% у одного источника и сухом втором также получаются `HasRain=false` и `UmbrellaYes`.

Рекомендация: описать единую политику риска, отдельно определять согласованность поставщиков и полноту данных. Выводить «возможен дождь, источники расходятся» вместо отрицания дождя при разногласии. Совпадение двух прогнозов не следует автоматически интерпретировать как числовую вероятность события.

### F7. Длительность осадков теряется, интервалы не объединяются

**Влияние: среднее. Приоритет: P2. Статус: подтверждено по коду и контрактам API.**

Места: `internal/weather/models.go`, `internal/weather/service.go:209–244`, `internal/weather/open_weather.go`, `internal/report/telegram.go:24–28`.

У каждого `RainInterval` начало равно концу, поэтому выводятся интервалы вида `15:00–15:00`. Точки разных источников просто добавляются подряд: нет общей сортировки, объединения, устранения повторов и происхождения интервала. При этом Open-Meteo возвращает почасовые значения, а OpenWeather — прогноз с шагом 3 часа и поле `rain.3h`. Сравнивать эти объёмы с одинаковым порогом без учёта длительности некорректно. Временную привязку каждого поля нужно сохранять по контракту поставщика. См. [Open-Meteo Forecast API](https://open-meteo.com/en/docs), [OpenWeather 5 day forecast](https://openweathermap.org/api/forecast5).

Рекомендация: включить в доменную модель начало/конец периода и источник, согласовать интенсивность осадков и вероятность с длительностью, затем объединять интервалы для пользовательского отчёта. `Confidence` сейчас является максимальным риском отдельной точки, а не оценкой достоверности; стоит разделить эти понятия.

### F8. Offset сбрасывается после пустого ответа, checkpoint недолговечен

**Влияние: среднее. Приоритет: P2. Статус: подтверждено статически.**

Места: `internal/bot/bot.go:107–108`, `internal/bot/handlers.go:63`.

Пустой ответ имеет `LastUpdateNumber=0`, после чего обработчик записывает `offset=1`, даже если до этого значение было большим. При перезапуске offset тоже теряется. Это нарушение монотонности checkpoint; само по себе оно не доказывает повторную доставку уже подтверждённых Telegram событий. Повторы необработанной пачки при ошибке описаны отдельно в F1. Семантика подтверждения через offset описана в [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates).

Рекомендация: на пустой пачке не менять checkpoint; сохранять индивидуальные `update_id` и выбрать явную стратегию доставки и восстановления после рестарта.

### F9. Некорректный HTTP_TIMEOUT может отключить защиту от зависаний

**Влияние: среднее. Приоритет: P2. Статус: значение `0s` воспроизведено.**

Места: `internal/config/config.go:15–20,33–43`, `main.go:30,45–46`.

`time.ParseDuration` принимает ноль и отрицательные длительности; конфигурация их не отклоняет. Нулевой тайм-аут клиента отключает общий лимит ожидания, а основной контекст создаётся через `context.Background()` без дедлайна. Невалидная строка, напротив, молча заменяется значением по умолчанию. Это ошибка конфигурационной устойчивости, а не установленная возможность обычного пользователя менять тайм-аут.

Рекомендация: `Load() (*Config, error)` с проверкой обязательных полей и положительного ограниченного тайм-аута; отдельные дедлайны для БД, провайдеров и команды. При ошибке завершать запуск с понятным сообщением без секретов.

### F10. Команда остановки уничтожает данные

**Влияние: высокое, потеря сохранённых локаций. Приоритет: P1. Статус: подтверждено статически; команда не выполнялась.**

Место: `Makefile:5–7`, обратная SQL-миграция.

`make stop` сначала вызывает `goose down`, который удаляет `user_locations`, затем `docker compose down -v`, удаляющий том PostgreSQL. Название команды не сообщает о разрушительном действии. Начальный `-` перед `goose` заставляет Make игнорировать ошибку отката; удаление тома продолжится.

Рекомендация: обычную остановку сделать без отката миграций и удаления томов. Очистку выделить в явную команду сброса локальных данных с защитой от запуска в рабочем окружении. Для ценных данных подготовить резервное копирование и проверить восстановление.

### F11. Ошибки запуска и завершение процесса плохо управляются

**Влияние: среднее. Приоритет: P2. Статус: подтверждено статически.**

Места: `main.go:22–42,58`, `internal/bot/handlers.go:43–64`.

При недоступности БД `main` печатает ошибку и делает `return`, поэтому процесс завершается с кодом успеха. Нет обработки SIGINT/SIGTERM через отменяемый контекст. `time.Sleep(2*time.Second)` не прерывается отменой. Состояние таблиц/миграций при запуске не проверяется: подключение к пустой БД может пройти Ping, но команды будут падать.

Рекомендации: функция `run() error`, ненулевой exit code при неуспешном запуске после освобождения ресурсов, `signal.NotifyContext`, ограниченный shutdown и дедлайны БД; миграции как явный шаг развёртывания с проверкой версии схемы. Мигрировать автоматически в каждом экземпляре приложения необязательно.

## 5. Архитектура, качество и эксплуатация

Базовое разделение пакетов стоит сохранить. PostgreSQL-репозиторий использует корректный upsert по `chat_id`; получение данных через `pgx.CollectOneRow` освобождает rows. Прогнозы не сохраняются в БД, а поставщики опрашиваются параллельно. Для Go 1.26 захват переменных цикла `range` в этих горутинах сам по себе не является ошибкой старой семантики Go.

Следующие изменения дадут практическую пользу:

| Область | Наблюдение | Улучшение | Приоритет |
| --- | --- | --- | --- |
| Тестирование | Нет ни одного `*_test.go` | Регрессии F1–F9, HTTP-контракты, renderer; интеграционные тесты upsert/чтения/отсутствующей записи на отдельной БД | P1 |
| Границы слоёв | Handler проверяет `pgx.ErrNoRows` напрямую | Доменная ошибка репозитория; интерфейс погодного сервиса для тестирования handler | P2 |
| Сборка зависимостей | Глобальная конфигурация загружается в `init()` | Явная загрузка и проверка в `run()`, удобная подмена в тестах | P2 |
| Telegram API | Нет обработки HTTP-статуса, `error_code`, `retry_after`; фиксированный опрос | Классификация ошибок, ограниченные повторы с backoff/jitter, long polling с отдельным тайм-аутом | P2 |
| Наблюдаемость | Только разрозненные `fmt.Println`, причины отказа источников теряются | Структурированные безопасные логи, длительность команд, очередь, доля ошибок провайдеров и отправки | P2 |
| Запуск | Нет README, Dockerfile приложения и CI; goose в Makefile не закреплён версией | Воспроизводимые инструкции и инструмент миграций, проверки test/vet/build/format и govulncheck в CI | P2 |
| БД | Нет CHECK для диапазона координат; нет эксплуатационных процедур | Проверки latitude/longitude, дедлайны операций, резервное копирование и контроль восстановления | P2 |
| Контейнеры | Compose описывает только БД, нет healthcheck | Отделить разработку от развёртывания, добавить проверку готовности и запуск приложения | P2 |
| План проекта | Пункт Compose ещё открыт, хотя `compose.yml` есть | Сверить план с фактическим состоянием; шаги 10 и 13 дополнить критериями отказоустойчивости | P3 |

Точечные интерфейсы и явные модели состояния полезнее дополнительного фреймворка. Микросервисы, брокер сообщений и Redis на текущем этапе не обоснованы: сначала достаточно ограниченной очереди и кеша в процессе, если измеренная нагрузка это допускает.

## 6. Пользовательское поведение и направления развития

### Сначала исправить доверие к ответу

Сводка должна однозначно показывать локацию, оставшийся горизонт, температуру, ожидаемый риск дождя, доступные источники и понятный совет. Сейчас `true/false`, `yes/optional/no`, `high/medium/low` попадают в русскоязычный интерфейс, а готовое поле `Umbrella.Text` вообще не используется.

Нужны состояния «нет данных», «один источник недоступен», «источники расходятся» и понятное сообщение о временном сбое. Для отчёта следует предусмотреть ограничение длины и разбиение: текущая модель не гарантирует, что произвольный будущий набор интервалов поместится в одно сообщение; это не воспроизведённый отказ текущего дневного прогноза. Ограничение текста описано в [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

### Затем улучшить выбор города и команды

Геокодер запрашивает `count=1` и молча выбирает первый результат. Для одноимённых населённых пунктов пользователь может получить прогноз другого города. Следует показывать несколько вариантов со страной/регионом и подтверждать выбранный город. Добавить `/location`, `/help`, удаление локации и при необходимости передачу координат через Telegram.

Команды вида `/weather@BotName` сейчас не распознаются и превращаются в `/start`. Для поддержки групп нужно нормализовать адресованные боту команды и использовать Telegram entities; изменение групповой локации ограничить согласно S5. Неизвестная команда должна приводить к краткой справке, а не выглядеть как новый старт.

### Расширение прогноза после стабилизации

1. Прогноз на ближайшие 3/6/12 часов и на завтра на основе единого контракта периодов.
2. Учитывать снег, смешанные осадки и грозу: сейчас доменная логика преимущественно ориентирована на дождь, а `precipitation_probability` может относиться к осадкам шире, чем поле `rain`.
3. Добавить ощущаемую температуру, ветер и предупреждения, если это помогает сценарию «как подготовиться к выходу».
4. Утренние подписки и уведомления о дожде — только после появления timezone-aware расписания, отписки, контроля дублей и общего бюджета отправки.
5. Оценивать качество советов по обратной связи и, при наличии данных, по фактическим наблюдениям. Сначала измерить пользу двух источников, затем решать, нужен ли третий.

Перед коммерческим запуском отдельно проверить условия использования API, атрибуцию и тарифные ограничения выбранных планов. Это не исследовалось как юридический аудит; наличие бесплатного endpoint не подтверждает пригодность для любого сценария.

## 7. Рекомендуемый порядок работ

| Этап | Работы | Критерий завершения |
| --- | --- | --- |
| 1. Защита данных и секретов | F10, S1–S3 | Обычная остановка сохраняет данные; реквизиты не фиксированы в коде запуска; тестовые секреты отсутствуют в логах |
| 2. Достоверность прогноза | F2–F7, F9 | Регрессии на период, температуры, пустые данные и согласованную rain-политику; ответ доступен при частичном отказе |

| 4. Воспроизводимость | CI, README, миграции, govulncheck, резервное копирование | Новый разработчик запускает проект по инструкции; CI проверяет поведение; восстановление БД проверено |
| 5. Развитие продукта | Выбор города, локализованный отчёт, команды, новые горизонты | Ответ понятен без технических значений enum; подтверждается выбранная локация; работают нужные команды |
| 6. Подписки и рост | Уведомления, измерение качества, масштабирование по метрикам | Управляемые квоты, отписка, отсутствие дублей и измеримая польза функции |

Оценку трудоёмкости стоит делать после фиксации контракта периодов и правил дождя: эти решения затрагивают провайдеры, агрегацию, renderer и тесты одновременно.

## 8. Регрессионные сценарии и ограничения аудита

### Что воспроизведено изолированно

| Проверка в копии проекта | Наблюдаемое ошибочное поведение |
| --- | --- |
| `TestAuditPartialFailure` | Один исправный и один ошибочный провайдер приводят к общей ошибке |
| `TestAuditNegativeMaximum` | Максимум источника −5 °C превращается в общий максимум 0 °C |
| `TestAuditZeroMinimum` | Минимум `[0, 5]` превращается в 5 °C |
| `TestAuditEmptyForecast` | Пустой прогноз считается доступным и приводит к `UmbrellaNo` |
| `TestAuditRainDisagreement` | 80% у одного источника и сухой второй дают `HasRain=false`, `UmbrellaYes` |
| `TestAuditTinyProbability` | 1% у обоих источников даёт `HasRain=false`, пустые интервалы и `UmbrellaYes` |
| `TestAuditMeteoPeriod` | В ответе периода с 17:00 остаётся точка 01:00 |
| `TestAuditZeroTimeout` | Конфигурация принимает `HTTP_TIMEOUT=0s` |
| `TestAuditTokenInError` | Сетевая ошибка `GetUpdates` содержит вымышленный токен |
| `TestAuditBatchStopsAtFailedMessage` | Ошибка ответа первому чату прерывает обработку второго |

Проверки расположены во временной копии `/tmp/weather-sum-audit-2026-10-18/internal/{weather,config,bot}/audit_test.go` и не добавлены в приложение. Они утверждают наличие дефектов; при исправлении соответствующие ожидания нужно заменить на правильное поведение. `/tmp` не является долговечным хранилищем. В пределах текущей сессии их можно повторить:

```bash
cd /tmp/weather-sum-audit-2026-10-18
GOCACHE=/tmp/weather-sum-audit-go-cache /usr/local/go/bin/go test -v ./internal/weather ./internal/config ./internal/bot
```

Дополнительно нужны постоянные тесты: монотонность offset после пустой пачки; необрабатываемое событие между успешными; отмена контекста; отказ всех источников; переход через полночь и DST; трёхчасовые осадки, пересекающие начало периода; неполные/null-данные API; ответы Telegram 429/403/5xx; репозиторий на отдельной PostgreSQL; сохранение данных после обычной остановки.

Не выполнялись: обращения с рабочими ключами, сквозная проверка реального Telegram, интеграционные проверки PostgreSQL, активное сетевое сканирование, нагрузочный тест, проверка восстановления backup, сканирование истории Git и актуальный vulnerability scan зависимостей. Соответственно, сквозная работоспособность и безопасность развёртывания остаются неподтверждёнными. Для последующего закрытия аудита следует выполнить `govulncheck ./...` в окружении с установленным инструментом и доступом к базе Go Vulnerability Database, затем разобрать достижимость найденных проблем, а не ограничиться номерами версий.
