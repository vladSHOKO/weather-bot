Основание: [AUDIT.md](AUDIT.md), 18 октября 2026 года.

Статус на 19 октября 2026, итерация 4: **аудит закрыт для стадии разработки**. Пользователь подтвердил отсутствие Git-истории и исключил деплой из задачи; живое тестирование бота разрешено и выполнено. Исправления и применимые проверки блоков 1–8 завершены, в том числе для реальной локальной БД. Подготовка рабочего окружения остаётся отдельным этапом [перед выпуском](docs/release-checklist.md), а не незавершённым исправлением кода.

## Порядок работы

Работаем по блокам: фиксируем ожидаемое поведение, исправляем, проверяем критерии готовности, записываем результат. Большой блок делим на небольшие изменения, которые можно проверить отдельно. Тесты добавляем вместе с исправлениями; не откладываем их до конца проекта.

Для каждого завершённого блока сохраняем: что изменилось, результаты проверок, оставшиеся ограничения. Замечание аудита закрываем только после проверки результата. Если проверка требует рабочего окружения, фиксируем это как незавершённую проверку, даже когда код уже готов.

| Блок | Результат | Приоритет | Зависимости |
| --- | --- | --- | --- |
| 1. Данные и секреты | Остановка сохраняет данные, секреты защищены, БД изолирована | P1, часть P2 | Нет |
| 2. Конфигурация и внешние вызовы | Предсказуемый запуск, завершение и обработка некорректных ответов | P1/P2 | 1 |
| 3. Доставка Telegram-событий | Ошибка сообщения не блокирует очередь; checkpoint корректен | P1/P2 | 2 |

Рекомендуемая последовательность: **1 → 2 → 3 → 4 → 5 → 6 → 7 → 8**. Блоки 3 и 4 технически независимы после блока 2. Подготовку README и CI можно вести по мере изменений; финальную проверку выполнять в блоке 8.

До использования с ценными данными нужно завершить защиту БД и проверить восстановление резервной копии. До публичного запуска — закрыть все P1 из аудита и выполнить проверки развёртывания. Наличие реализованного кода без эксплуатационной проверки недостаточно.

### Результат блока 1 — 18 октября 2026 года

Реализованы безопасная остановка, отдельный `reset-local` с двумя явными условиями, локальная привязка порта БД, реквизиты через окружение, подготовка ролей и явные права на `user_locations`. Пароли ролей задаются через интерактивный `psql \password`. Добавлены `.gitignore`, `.dockerignore`, права `.env` изменены на `0600` без изменения содержимого.

На границах Telegram/OpenWeather и при выводе ошибок приложения применяется `internal/safeerror`: произвольные сообщения причин не печатаются, `errors.Is`/`errors.As` сохранены. Постоянные Go-тесты проверяют синтетические DNS/TLS/timeout/connection-ошибки, обёрнутые причины, ошибку с URL БД и описание ответа Telegram.

Выполнены `go test ./...`, `go vet ./...`, проверки с race detector для затронутых пакетов и сборка с отключением недоступных VCS-метаданных. Интеграционный сценарий `tests/integration/block-01.sh` прошёл на отдельном Compose-проекте PostgreSQL 16: CRUD, запрет DDL/создания ролей/чтения миграционных метаданных, повторное применение скрипта ролей, сохранность после остановки, loopback и отказ сброса без условий. Тестовые контейнеры и том удалены.

Инструкция: [docs/database-security.md](docs/database-security.md).

Открыто: история Git недоступна; реальные логи и сетевой доступ с другого хоста не проверены. Роли, пароли, владельцы таблиц и строки подключения существующей рабочей БД не менялись. При её настройке требуется проверить вход по новым паролям, владельцев и отсутствие прежних избыточных прав. Контейнер приложения и удаление публикации порта в конфигурации развёртывания относятся к блоку 8; сейчас этот сценарий описан в инструкции. Поэтому S1/S3 целиком ещё не закрыты для рабочего окружения. Защита `reset-local` проверяет явные параметры, но не определяет автоматически назначение Docker context.

## Блок 6. Команды, выбор локации и понятный отчёт

**Замечания:** S5, раздел 6 аудита, отображение ограничений из F2/F5/F6/F7.

Цель: пользователь понимает, где, когда и насколько полно получен прогноз, и может управлять сохранёнными данными.

2. **Причины отказа:** `Finish` принимает ограниченный `FailureCode`, отклоняет произвольный текст; сохраняются безопасные классы timeout/network/HTTP/invalid response/no data и отдельный `attempts_exhausted`. Для обычных неизвестных ошибок остаётся `command_failed`. Формат БД совместим, новая миграция не требуется.
3. **Backup:** файл готовой копии появляется только после успешного `pg_dump`, проверки размера и `pg_restore --list`. Атомарная публикация не перезаписывает существующее имя; ошибка не запускает ротацию. Проверены частичный/пустой/повреждённый dump, коллизия, права и удаление временных файлов. Интеграция теперь восстанавливает архив именно эксплуатационного скрипта.
4. **Healthcheck:** `.env` читается до обработки `-healthcheck`; переменные окружения сохраняют приоритет. Добавлена регрессия выбора адреса без обращения к реальной сети.
5. **Приёмка deploy Compose:** добавлены `make test-deploy`, `tests/integration/deploy.sh`, тестовый HTTPS-сервер и отдельный Docker target `test-api`. Настоящие runtime и migrator проверяются с синтетическими ключами и отдельными паролями ролей. API заменены сетевыми aliases и временным доверенным CA; сети теста закрыты для внешнего трафика. Проверены конфигурация, неподготовленная/недоступная БД, команды, readiness, UID/read-only/capabilities, отсутствие опубликованного порта БД и рестарт. CI дополнен этой проверкой.
6. **Дополнительные регрессии:** реальные исполнители на PostgreSQL проходят HTTP 403/429/503 с конечным бюджетом и `retry_after`. SQL-триггеры моделируют отказ ingestion и записи completion после успешной внешней отправки. Добавлены общие периоды двух провайдеров, UTC/Kathmandu, DST 23/25 часов, пересечение конца периода без перерасчёта объёма, значения выше порогов риска и состояния отчёта.
