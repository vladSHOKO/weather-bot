# Raincheck / weather-sum

Telegram-бот, который объединяет прогнозы Open-Meteo и настроенных дополнительных источников: MET Norway, WeatherAPI.com, OpenWeather. Работает в личных чатах; прогноз показывает остаток сегодняшнего дня или весь завтрашний день в часовом поясе выбранного города.

## Локальный запуск

Требуются Go **1.26.9 или новее**, Docker с Compose, GNU Make. Для проверок нужны Bash и Python 3, для `make test-deploy` — также OpenSSL. Версии утилит закреплены в Makefile: goose v3.27.2, govulncheck v1.9.0, Gitleaks v8.28.0.

1. Создать `.env` из `.env.example`, если своего файла ещё нет; установить права `chmod 600 .env`.
2. Заполнить `POSTGRES_PASSWORD` случайным уникальным паролем и `TELEGRAM_BOT_TOKEN` токеном отдельного бота. Дополнительные погодные источники необязательны; см. [подключение бесплатных сервисов](docs/weather-sources.md).
3. Подготовить роли, задать пароли и строки подключения по [инструкции БД](docs/database-security.md).

```bash
make tools
make start
make db-roles
make db-passwords
# Заполнить DATABASE_URL (weather_app) и GOOSE_DBSTRING (weather_migrator).
make migrate
make db-grants
go run .
```

Goose и govulncheck должны находиться в PATH; обычно это каталог `go/bin` пользователя. При необходимости передать путь через `make migrate GOOSE=/path/to/goose`.

`make stop` сохраняет данные. Разрушительный сброс вынесен в `make reset-local` с явными условиями; см. инструкцию БД. Существующие `.env`, пароли и владельцы объектов автоматически не переписываются.

Для существующей установки сначала сделать backup, применить новую миграцию `20261018000000`, повторно выдать права через `make db-grants`, затем перезапустить приложение. Новая миграция добавляет долговечную очередь и проверки координат. Если старые данные нарушают ограничения, миграция остановится: исправить записи отдельно, не сбрасывать том.

## Команды

| Команда | Поведение |
| --- | --- |
| `/start` | Приветствие, постоянное меню и кнопка выбора города |
| `/help` | Справка и сведения о хранении данных |
| `/setlocation [город]` | Запрос названия города, затем до пяти вариантов с кнопками подтверждения |
| `/choose код номер` | Совместимый способ подтверждения; основной выбор выполняется кнопками |
| `/location` | Сохранённая локация |
| `/weather` | Сводка от текущего времени до местной полуночи |
| `/tomorrow` | Прогноз на весь завтрашний день, от местной полуночи до следующей |
| `/deletelocation` | Запрос подтверждения удаления сохранённой локации |
| `/cancel` | Отмена текущего диалога |

В постоянном меню доступны «🌤 Погода», «📍 Выбрать город», «📌 Мой город» и «Помощь». После выбора города введите название обычным сообщением. Если город не найден, можно сразу уточнить название без повторения команды. После сохранения доступны кнопки прогноза и смены города. Удаление доступно из «Мой город» и требует подтверждения. Нажатие «Погода», «Мой город», «Помощь» или «Отмена» завершает текущий диалог. Диалог и подтверждения действуют 5 минут; устаревший выбор предлагает начать заново кнопкой.

Команды с `@имя_бота` поддерживаются. Команды другому боту игнорируются. Группы не имеют доступа к личным локациям. После рестарта незавершённый выбор города нужно начать заново.

## Погодные источники

Бесплатные подключения, регистрация и переменные окружения описаны в [инструкции](docs/weather-sources.md). Новые источники включаются автоматически после заполнения настроек и перезапуска. Недоступный источник отмечается в «Подробнее»; оставшиеся продолжают работать.

## Прогноз и ограничения данных

Основной ответ — короткая сводка: город, температура, окна возможных осадков и совет про зонт. Соседние дождевые интервалы объединяются, сухие промежутки сохраняются; отображаются до трёх окон. Если данных недостаточно или прогнозы расходятся, остаётся короткая пометка о неопределённости. Подписи источников и лицензия оформлены строкой ссылок без превью.

Команда `/tomorrow` показывает весь завтрашний день в часовом поясе выбранного города; в заголовке указаны «завтра» и дата. Границы календарного дня учитывают перевод часов, поэтому период может длиться 23, 24 или 25 часов.

Под сводкой доступны «Обновить» и «Подробнее». Для завтрашнего прогноза обе кнопки сохраняют выбранный день, в том числе кнопка восстановления устаревших подробностей. Обновление заново рассчитывает остаток дня, используя действующий погодный кеш. Подробности показывают источники, их доступность, часовой пояс, риски и покрытие именно показанной сводки без новых запросов к API. В памяти хранится только текст последних подробностей для чата: до 30 минут и не позже конца дня, максимум 1024 чата. Новый прогноз, смена или удаление города делают прежние подробности недействительными; после рестарта или истечения срока кнопка предлагает обновить прогноз.

Источники получают общий период. Для WeatherAPI используются часовые интервалы вперёд от `time_epoch`; для MET Norway — `next_1_hours`, а при их отсутствии — доступные `next_6_hours` или `next_12_hours`. Накопления на 6 часов не превращаются в почасовые измерения. В compact-прогнозе MET Norway нет вероятности осадков; риск оценивается по количеству осадков. Вероятности дождя и снега WeatherAPI не складываются: берётся наибольшая из доступных оценок как показатель риска, а не вычисленная вероятность любого вида осадков. Температура — минимум/максимум доступных мгновенных значений внутри периода. Ноль и отрицательные температуры являются обычными значениями; отсутствие данных показывается отдельно.

Почасовые и трёхчасовые осадки сохраняют исходную длительность. Риск определяется по вероятности или средней интенсивности в исходном интервале: небольшой — от 20% либо положительная интенсивность, умеренный — от 40% либо 0.2 мм/ч, высокий — от 70% либо 1 мм/ч. Это эвристика совета, а не измеренная точность прогноза. Доля согласных источников не превращается в вероятность.

При пересечении границы прогноза интервал помечается; накопленные осадки не делятся пропорционально оставшейся части. Общая вероятность осадков может включать снег; отчёт использует слово «осадки». Источники, разногласия и неполное покрытие видны пользователю. Пустой ответ или отказ всех источников не означает сухую погоду.

Окружение имеет приоритет над `.env`. Ошибочные значения останавливают запуск с ненулевым кодом. Указанные верхние границы не означают, что максимальные значения подходят конкретному серверу.

## Очередь, кеш и повторы

Один экземпляр poller на БД защищён PostgreSQL advisory lock. Сначала пачка атомарно сохраняется вместе с checkpoint, затем подтверждается Telegram. Пустая пачка не меняет offset. Исполнители обрабатывают разные чаты параллельно; более поздняя команда одного чата не обгоняет раннюю, в том числе при отложенном повторе.

Временные сетевые ошибки, 429 и 5xx повторяются с ограничением попыток, backoff/jitter и учётом `retry_after`. Постоянные ошибки и исчерпанные попытки завершают событие с безопасным кодом ошибки. Ошибки БД при учёте событий останавливают процесс; восстановление переводит незавершённые события в очередь. Возможен повтор внешней отправки, если процесс упал после успешного `sendMessage`, но до сохранения результата; exactly-once не обещается.

Завершённые отказы сохраняют только ограниченный код причины: `timeout`, `network_error`, `http_403`, `http_429`, `http_4xx`, `http_5xx`, `invalid_response`, `no_forecast_data`, `canceled` или `command_failed`. Восстановленное событие с исчерпанным бюджетом получает `attempts_exhausted`. Произвольный текст ошибок в inbox не записывается.

Для одного чата допускается до 20 незавершённых событий. При переполнении этого лимита последующие события чата подтверждаются без выполнения. При заполнении общей очереди новая пачка не подтверждается до освобождения места. Это явная политика защиты от спама, а не гарантия исполнения любого количества команд.

Погодный кеш ограничен по размеру и сроку; ключ включает координаты, timezone и местную дату. Кешируются исходные данные, фильтрация по текущему времени выполняется заново. Одновременные одинаковые обращения объединяются; отмена одного клиента не отменяет общий ограниченный запрос. Ошибки и пустые прогнозы не кешируются общим кешем. MET Norway дополнительно использует HTTP-кеш по округлённым координатам: до `Expires` повторного запроса нет, затем отправляется `If-Modified-Since`; `304` продлевает кеш. При заполнении MET-кеша новые координаты временно не обслуживаются, чтобы не вытеснять свежие ответы и не запрашивать их раньше `Expires`. Ответ `429` временно блокирует новые обращения к MET с учётом `Retry-After`. Геокодинг кешируется до 10 минут, до 64 записей без привязки к пользователю.

Текст завершённых событий удаляется сразу, chat_id обнуляется; служебные записи удаляются через 7 дней небольшими порциями. Пока событие ожидает или повторяется, его текст хранится в БД. Выбор города хранится в памяти до 5 минут. Удаление локации не отменяет последующие команды, явно отправленные пользователем.

## Проверки

```bash
make check
go test -race ./...
make test-integration
make test-deploy
make check-secrets
govulncheck ./...
```

Обычные Go-тесты не требуют рабочих ключей. Тесты БД пропускаются без `TEST_DATABASE_URL`; `make test-integration` создаёт отдельную PostgreSQL и запускает их, проверяет реальные миграции и восстановление backup. Тестовый скрипт не загружает рабочий `.env`, удаляет только свой Compose-проект и не должен запускаться с `TEST_DATABASE_URL`, указывающим на рабочую БД.

`make check` также проверяет поведение backup при частичном, пустом и повреждённом архиве, коллизии имени и ротации. `make test-deploy` собирает runtime, migrator и тестовый HTTPS-сервер и запускает отдельный проект на основе `compose.deploy.yml`: настоящие миграции и вход под ролями приложения/миграций, команды, перезапуск, healthcheck, отсутствие публикации БД и настройки прав контейнера. API подменены внутри изолированной сети; рабочие ключи и `.env` не используются. Тестовый CA существует только в этом стенде. Временные контейнеры и том удаляются по завершении; файлы диагностики остаются в `/tmp/weather-sum-deploy.*`.

`make check-secrets` сканирует исходники через Gitleaks с редактированием секретов в выводе. Локальные `.env` и служебные каталоги исключены из копии исходников; отслеживаемые Git файлы добавляются обратно, даже если попали в исключения. При наличии коммитов сканируется вся история. В текущем проекте Git-история ещё не ведётся. Самопроверка скрипта подтвердила обнаружение синтетического секрета в tracked `.env` и после его удаления из рабочей копии.

Живые проверки отключены в обычных тестах. `make test-live-identity` проверяет только `getMe`, без отправки сообщений. `LIVE_SMOKE_CHAT_ID=<свой chat_id> make test-live` отправляет до 11 ответов в явно разрешённый личный чат: справку, выбор города, прогноз, частичный отказ, пересоздание обработчика и удаление. Используются настоящий Telegram и погодные API, но временный repository в памяти; существующая БД не подключается, входящие события Telegram не подтверждаются. Тест предназначен для разработки и требует предварительного согласия владельца чата. Переменные окружения имеют приоритет над `.env`. Одноразовый `TestLiveResolveChat` умеет подтвердить чат через уникальную команду, сохранив цель в защищённый файл с ограниченным сроком действия.

CI проверяет форматирование, тесты, race detector, vet, сборку, уязвимости, интеграцию, контейнеры и историю на секреты. Сам запуск GitHub Actions в этом локальном окружении не выполняется.

## Развёртывание и наблюдение

Для запуска бинарника на сервере без Docker см. [деплой через systemd](docs/systemd-deployment.md).

См. [инструкцию эксплуатации](docs/operations.md). Использовать `compose.deploy.yml`: БД доступна только во внутренней сети, приложение запускается без root и без права записи в файловую систему образа. Рабочие ключи и внешние сервисы не входят в автоматический тестовый стенд.

- `GET /healthz` проверяет доступность БД и состояние процесса.
- `GET /metrics` возвращает агрегированные JSON-счётчики и состояние очереди без chat_id и текста команд.
- `weather-sum -healthcheck` возвращает ненулевой код при недоступности локального readiness endpoint.
- Логи структурированы, URL с токенами и произвольные сообщения внешних ошибок не выводятся.

История изменений и ограничения приёмки: [план исправлений](REMEDIATION_PLAN.md), [результаты проверки](docs/verification.md). Исходный [аудит](AUDIT.md) сохраняет состояние до исправлений.

Аудит закрыт для стадии разработки; условия будущего рабочего выпуска вынесены в [отдельный список](docs/release-checklist.md). Развёртывание и постоянный запуск приложения в текущую задачу не входят.
